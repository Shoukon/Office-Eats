# PERF-02：同步等待與跨 Session 唯讀快照

基準：`452a8ae31eedf2d108fa3007e43fcb816b1e1b9d`（包含 PR #14）；版本維持 v3.8.0。正式資料、Secrets、GitHub 備份均未讀取。

## 實測方法

- Windows 本機既有 Python 3.12.14 runtime；隔離 SQLite、FakeRemote；urllib 真實連線被阻擋。
- 每組 3 次；10／500 筆假訂單；GET／PUT 延遲 0／0、50／50、500／0 ms。四種資料異動各測，另測六種遠端失敗情境。
- 本機新增／編輯／刪除走 BackupGuard；店家以相同寫入包裝器單一交易更新兩個名稱。本機時間包含安全標記與提交，但不含瀏覽器事件。
- 另一 Session 在 GET 開始時啟動 order_snapshot。讀取總時間包含 SQLite 查詢與協調等待，沒有把兩者差值當成精確鎖等待時間。
- total_ms 直接從本機異動開始計到 transfer 返回（含測試準備快照及執行緒排程）；local_to_sync_ms 只是本機交易與 transfer 時間相加。兩者都不是 UI 端到端量測。GET/PUT 為 FakeRemote 回呼時間；真實網路及前端時間未知。
- 快照、驗證、序列化、加解密另做每組 5 次獨立微量測；加密包含序列化，解密包含驗證，不能相加視為總時間。
- 正式前後比較採 measured-before.json 與 measured-after.json；後者在其他測試結束後執行。第一輪 after.json／after-quiet.json 僅診斷，不列入下表。

可重跑：`PYTHONPATH=tests;. python -B tests/benchmark_sync_wait.py --output new-measurement.json`。輸出只能是本 worktree `.test-tmp` 內的新檔名，拒絕覆寫。基準比較應在指定 main commit 的隔離副本執行同一腳本，不使用正式程式初始化。

## 採用方案與安全邊界

- 寫入、同步、匯入、SHA 判斷、未知 PUT 核對仍持有原來的同檔案排他鎖；所有真實交易／提交前 pending 保護保持原狀。
- 一般同步在排他鎖下取得 committed 本機快照後，將目前 `order_generation` 綁定至可選的本機 journal 欄位 `read_generation`。這只允許快照讀取，不代表備份成功，不授予寫入權。
- order_snapshot/member_snapshot 可在 SQLite `BEGIN` 一致讀取交易內取 committed rows；前後兩次 journal 必須都允許相同 generation。所有寫入仍重新驗證原 token。
- 匯入先公布新的 order_generation；舊 read_generation 不會被同步改成新值，因此「新代次已公布、資料尚未提交」窗口不會把舊訂單綁成新身分。缺少綁定、代次變化或狀態不確定一律退回原排他鎖。
- 不在匯入 transaction 中建立新讀取綁定。匯入／回滾後，等下一次一般同步在原鎖下確認 committed epoch 才重新綁定。既有 journal 無此欄位時仍使用原讀取路徑，不需要資料遷移。
- Windows 初次高頻量測實際發現 JSON 讀取／原子 replace 分享競爭；新增獨立短 journal I/O 鎖，只跨越 read／fsync／replace，不跨越網路。讀取釋放 journal 鎖後才讀 SQLite，關閉 SQLite 後才核對 journal，避免與寫入鎖形成反向等待。
- 新增 `.safety.json.lock` 已受既有 `.gitignore` 規則涵蓋。4.1 備份、Fernet、資料表及應用版本不變。
- 僅同一檔案系統、且所有存取者使用此 BackupGuard 協定。不是跨 Cloud 實例的全域鎖，不合併不同實例資料，也不保證未同步資料在實例重建後存在。
- 完整 app rerun 仍會經過 prepare/startup 與選項初始化，編輯的 expected_order 及其他寫入意圖也仍走原鎖；這些路徑可能繼續等待網路中的同步。本批只減少已綁定 epoch 的 order_snapshot/member_snapshot 阻塞，不宣稱所有 Session 操作皆已非阻塞。
- 不採背景同步：沒有引入持久化佇列、worker、重試或新的恢復狀態機。不縮短寫入鎖或略過 SHA／資料驗證。
