# 備份、部署與復原

## P2-03：備份目的地（待負責人決策，尚未遷移）

目前 get_github_settings() 的 branch 預設 main、data_file 預設 order_data.json，
備份以 GitHub Contents API 的 SHA 比對更新加密檔。Cloud 已觀察的來源是
Shoukon/Office-Eats、main、order.py。程式已支援獨立分支或另一個 repository；
切換需要正式設定及存取權限，這份文件不代表已核准或已執行。

| 方案 | 效益 | 成本／風險 |
|---|---|---|
| 同 repository 的專用 backup-data 分支 | 不再因備份提交改動部署 main；沿用現有 API | 權限隔離有限；所有寫入者必須同時切換；舊 SHA 基準需核對 |
| 獨立私人備份 repository | 更清楚的程式／資料權限與保留政策 | 需負責人建立及核准權限；復原設定更多 |

建議先選同 repository 專用分支，前提是負責人接受其權限範圍。
不要為此修改 4.1 格式、輪替 Fernet key 或刪除 main 上既有加密備份。

### 最小遷移與回復順序（本批不執行）

1. 在假 repository／FakeRemote 完整演練啟動、同步、SHA 衝突及還原。
2. 負責人核准目的地及維護時段，暫停所有寫入者；確認沒有未決 PUT，
   本機與舊遠端摘要一致。保留 SQLite 一致快照、本機安全狀態、
   加密備份及受限制存取的 JSON 匯出；key 由原保管人另外妥善保存，不寫進報告。
3. 由負責人在新目的地放置經驗證可解密的相同資料；比較業務摘要，
   確認不是空備份。保留舊目的地。不能僅以檔名相同認定內容相同。
4. 所有寫入者必須停止後才能切換。新目的地的 blob SHA 必須與本機基準核對；
   重新加密即使內容相同也會改變 SHA，不可手改 .safety.json 偽造基準。
   最安全的演練是使用全新測試資料庫，首次從新目的地還原、建立新 journal，
   驗證後才由負責人決定正式切換方式。既有實例出現衝突時停止，不強制覆寫。
5. 確認新實例還原、唯讀核對、單一假操作往返及舊 Session 拒絕測試後，
   正式是否開放寫入由負責人決定。不可用正式訂單作破壞性測試。
6. 若尚未開放新寫入，可由負責人回復原設定及原資料套件。
   若新目的地已有新增資料，不能直接切回較舊備份；先暫停寫入、匯出雙方、
   人工核對增量並演練匯入，避免回復本身造成資料遺失。

本流程的待決策事項：目的地、資料保留政策、維護時段、設定權限與復原負責人。
本批未切換正式分支、repository、Secrets 或 Cloud 設定。
