# 備份、部署與復原

## P2-03：備份目的地（待負責人決策，尚未遷移）

目前 get_github_settings() 的 branch 預設 main、data_file 預設 order_data.json，
備份以 GitHub Contents API 的 SHA 比對更新加密檔。Cloud 已觀察的來源是
Shoukon/Office-Eats、main、order.py。程式已支援獨立分支或另一個 repository；
切換需要正式設定及存取權限，這份文件不代表已核准或已執行。

| 方案 | 效益 | 成本／風險 |
|---|---|---|
| 同 repository 的專用 backup-data 分支 | 不再因備份提交改動部署 main；沿用現有 API | 權限隔離有限；所有寫入者必須同時切換；舊 SHA 基準需核對 |
| 獨立私人備份 repository | 更清楚的程式／資料權限與保留政策 | 需負責人建立及核准權限；復原設定更多 |

建議先選同 repository 專用分支，前提是負責人接受其權限範圍。
不要為此修改 4.1 格式、輪替 Fernet key 或刪除 main 上既有加密備份。

### 最小遷移與回復順序（本批不執行）

1. 在假 repository／FakeRemote 完整演練啟動、同步、SHA 衝突及還原。
2. 負責人核准目的地及維護時段，暫停所有寫入者；確認沒有未決 PUT，
   本機與舊遠端摘要一致。保留 SQLite 一致快照、本機安全狀態、
   加密備份及受限制存取的 JSON 匯出；key 由原保管人另外妥善保存，不寫進報告。
3. 由負責人在新目的地放置經驗證可解密的相同資料；比較業務摘要，
   確認不是空備份。保留舊目的地。不能僅以檔名相同認定內容相同。
4. 所有寫入者必須停止後才能切換。新目的地的 blob SHA 必須與本機基準核對；
   重新加密即使內容相同也會改變 SHA，不可手改 .safety.json 偽造基準。
   最安全的演練是使用全新測試資料庫，首次從新目的地還原、建立新 journal，
   驗證後才由負責人決定正式切換方式。既有實例出現衝突時停止，不強制覆寫。
5. 確認新實例還原、唯讀核對、單一假操作往返及舊 Session 拒絕測試後，
   正式是否開放寫入由負責人決定。不可用正式訂單作破壞性測試。
6. 若尚未開放新寫入，可由負責人回復原設定及原資料套件。
   若新目的地已有新增資料，不能直接切回較舊備份；先暫停寫入、匯出雙方、
   人工核對增量並演練匯入，避免回復本身造成資料遺失。

本流程的待決策事項：目的地、資料保留政策、維護時段、設定權限與復原負責人。
本批未切換正式分支、repository、Secrets 或 Cloud 設定。


## P2-04：單一寫入假設與異常處理

目前只保證同一 SQLite 檔案上的 BEGIN IMMEDIATE 與 OS 檔案鎖。
不同 Cloud 實例的本機磁碟不共享；GitHub SHA 能拒絕較舊寫入，不能合併兩邊訂單。
部署目前只有一個已觀察應用入口，不代表平台保證永遠只有一個實例。
重建、重新部署或生命週期結束時，尚未同步的本機資料可能無法復原。
沒有已確認的多實例業務需求，本批不遷移資料庫。

### 日常核對

管理員查看「GitHub 永久資料」及主頁警告。成功代表最後確認內容與目前本機摘要相符；
不是未來遠端永遠不變的保證。保留最後成功時間；不要用 Keep Alive 成功當部署證據。

| 狀態／情況 | 可執行步驟 | 必須停止的操作 |
|---|---|---|
| pending、未決 attempt 為空 | 用「唯讀核對 GitHub 備份」確認；失敗保留警告。若確知只有本機新增且基準未變，再手動同步 | 不因警告而清空資料或刪 journal |
| 網路／權限失效 | 先限制新寫入並由管理員匯出本機 JSON 到受保護位置；修復連線／權限後核對 | 不把重新啟動當修復，不在對話貼 Token |
| 遠端版本衝突 | 暫停所有寫入者，分別保留本機與遠端可驗證快照，人工比對差異 | 不強制 PUT、不採用最新 SHA 後盲目上傳 |
| PUT timeout／回應遺失、未決 attempt | 原程式會阻擋後續修改；手動同步入口只先核對原 attempt，不盲目重送。稍後再核對 | 不刪 journal、不重新匯入舊快照；無法確認則交由負責人處理 |
| 首次接管不一致／狀態檔損毀 | 保留原始資料與狀態，停止寫入，人工判斷來源 | 不把它當首次空資料庫，不任意重設 baseline |

### 復原順序

1. 暫停所有寫入者，先保存仍可取得的本機 JSON、遠端加密備份及對應版本資訊。
   匯出 JSON 是明文業務資料，放在受限制位置，不提交 Git、不上傳 CI artifact。
   SQLite 實體快照應用 SQLite backup API 或在所有連線關閉後取得，不能在寫入中
   單獨複製 DB 並忽略 WAL／journal。保留本機 .safety.json、.safety.lock 的關聯資訊；
   OS 鎖不會靠複製 lock 檔變成跨機鎖。
2. Cloud 管理 UI 並不提供完整 DB／journal 下載功能。如果無法保存尚未同步內容，
   不得先重啟／重新部署來清除錯誤；應先請平台或環境負責人協助保全。
3. 在隔離環境以假憑證／唯讀副本驗證格式、Fernet 解密與資料內容，核對四張業務表、
   店家、名單、數量、金額、付款狀態及舊格式相容性。原 key 不得寫入命令紀錄、Git 或報告。
4. 若本機與遠端不同，列出雙方差異，由資料負責人決定來源。不可自動覆寫其中一方，
   也不可僅因遠端提交較新就認定其包含全部訂單。
5. 先用隔離新資料庫測試首次還原或合法 JSON 匯入，確認成功與錯誤回滾、SHA 衝突、
   匯出往返。正式匯入會替換四張業務表且同步遠端，必須另行核准並保留回復套件。
6. 正式操作後重新選名，舊 Session 的 token 可能已失效；確認所有資料與付款一致、
   備份已確認成功，才恢復寫入。不要透過人工修 journal 解除阻擋。

回復本身若遇到不明 PUT、資料不一致或未驗證備份，停止；這份指引不是授權破壞性操作。
